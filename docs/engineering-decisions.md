# 工程決策與演進

本文件由既有提交、修復報告與 2026-09-21 驗證紀錄整理，說明問題、採取的做法與仍存在的代價。它不是各次提交當時撰寫的 ADR，也不以提交者數量或 commit 數量推算個人貢獻。

## 從功能串接到可靠的行程操作

2026 年 4 月的工作以登入、行程資料、資料夾與協作等應用流程為主。5 月加入影片分析、模型服務整合、自然對話與結構化行程動作；6 月處理記憶、地圖還原、破壞性操作與交易式儲存；9 月再集中處理字幕證據、背景工作、串流與競態回歸。

主線保留 `omen`、`maomi09` 等分支的合併歷史。2026-09-21 的 `7cb2d2b` 整合了較多變更，因此不能只依單一提交標題推論所有細節；需併讀檔案差異與驗證報告。2026-10-04 核對時，`main` 與 `master` 的程式基準相同，GitHub 預設分支為 `master`。

## 決策一：讓模型提出結構化動作，由程式驗證與執行

**問題。** 自然語言中的「詢問」「新增」「替換」「清空」很容易混淆。曾出現「刪掉第二天的晴空塔」被擴大成清空第二天，以及部分操作失敗卻顯示全部完成。

**實作。** 加入對話協調器、AssistantAction schema、動作驗證與前端執行器。對整天清空等操作設確認狀態，並回報成功、略過、失敗結果。同一訊息的重複動作使用穩定識別避免再次新增。

**取捨。** 規則容易回歸測試，也能把操作範圍限制在明確型別；但規則及模型仍需處理同義句、否定與指代，不代表已解決所有語言理解問題。動作冪等目前主要覆蓋 client replay，不是通用資料庫冪等表。

證據：`9fd70ac`、`54002bc`、`aecd83b`、`7cb2d2b`；[對話修復報告](../aiyo/docs/qa/conversation-remediation-report.md)。

## 決策二：以交易與版本檢查處理行程一致性

**問題。** 多個 Prisma 寫入分開執行會留下半份行程；儲存與地點補全的舊回應又可能覆蓋新編輯。曾以延遲回應重現更名遺失及刪除後活動復原。

**實作。** 行程整體寫入使用 transaction。前端儲存序列化並保留待送修改；切換行程或帳號後忽略舊回應；背景地點與照片補全檢查行程版本。活動使用 UUID，跨行程碰撞時同步重建標記連結。

**取捨。** transaction 確保單次寫入原子性，版本檢查阻止過期本機工作覆蓋新狀態；兩者仍不能取代多使用者同時編輯的衝突合併協定。

證據：`aecd83b`、`7cb2d2b`；[同步服務](../aiyo/src/services/syncService.ts)、[資料服務](../aiyo/src/server/data/appStateService.ts)。

## 決策三：以來源片段決定影片時間，不接受無依據的精確度

**問題。** 字幕單位混用曾把 5 秒誤判成 5000 秒；描述 fallback 曾以固定時間間隔產生片段。數字格式正確，卻不代表能跳到正確內容。

**實作。** 依字幕來源格式正規化秒數；模型引用片段 ID，再由程式回推時間。缺少時間來源時保留摘要與地點候選，不提供假的跳轉。更新 pipeline 版本避免讀回舊結果。

**取捨。** 對外呈現的片段可能減少，但每個時間的來源較可追查。無字幕、招牌只出現在畫面、口語地名辨識錯誤等仍需另外評估 ASR／視覺資料。

證據：`7cb2d2b`；[groundedVideoSegments.ts](../aiyo/src/server/video/groundedVideoSegments.ts)、[稽核報告](../aiyo/docs/optimization-audit-2026-09-21.md)。

## 決策四：使用持久佇列處理長工作

**問題。** 影片 HTTP 請求等待字幕、模型與地點查詢全部完成，記憶寫入也延長聊天等待；關閉或重新整理頁面後難以追蹤進度。

**實作。** 導入 BullMQ／Redis 與獨立 worker。影片採提交／查狀態模式，記憶寫入另設 queue；配置重試、保留上限與擁有者檢查。地點解析加入有限並行及單次分析共用結果。

**取捨。** 多一個需監控的背景程序與 Redis 持久資料。排隊改善故障恢復，不能讓模型本身更快；同時增加推論工作可能造成模型競爭。記憶 enqueue 失敗目前也沒有資料庫 outbox 保證補寫。

證據：`7cb2d2b`；[工作佇列](../aiyo/src/server/jobs)、[驗證報告](../aiyo/docs/optimization-verification-2026-09-21.md)。

## 決策五：偏好必須影響候選結果，而不只出現在提示文字

**問題。** 有保存偏好不代表規劃時真的使用；純文字「沿用」曾沒有把設定帶進規劃器，預設空排除清單也曾遮蔽舊設定。

**實作。** 確認沿用後合併偏好，以本次明示內容優先；搜尋與規劃共用候選排序。排序按實際名稱與場所類別處理興趣、必去及排除。區分規劃過與明確去過的歷史。

**取捨。** 此方法可解釋且容易檢查，但不等於推薦模型或完整限制求解。不能因店家資料缺少價格或飲食資訊就自動視為符合偏好。

證據：`fc924b2`、`3befca7`、`7cb2d2b`；[placePreferenceRanking.ts](../aiyo/src/server/personalization/placePreferenceRanking.ts)。

## 決策六：將地圖顯示、地點解析與交通能力分開

**問題。** 地點名稱可搜尋，不代表分店匹配；有經緯度，也可能只是城市中心。替換名稱時若沿用舊座標，畫面會看似完整但指向錯誤位置。

**實作。** 清理口語地點候選、排除泛稱、檢查地理結果品質；名稱更換時清除舊地點資料。採 MapLibre 呈現，透過 Photon／Overpass／OSRM 分別取得地點與路線，區分真實路線及示意線。

**取捨。** 多個 provider 的可用性與覆蓋不同，仍須處理缺值、同名及跨城市問題。地圖主流程的替換，不代表全球公共運輸或營業資料也同時齊備。

證據：`a8b3c52`、`7cb2d2b`；[地理品質報告](../aiyo/docs/testing/location-geocode-quality-report.md)。

## 後續可研究的問題

以下是尚待實驗的方向，不是已證明的成果：

| 問題 | 可比較的方法 | 所需證據 |
| --- | --- | --- |
| 證據約束是否降低影片錯誤時間與地點？ | 模型直接生成 vs. 片段 ID 對齊 | 人工標註地點與時間，計算 precision／recall、時間誤差 |
| 偏好排序是否改善選點？ | 無排序 vs. 規則排序；本次條件覆蓋開關 | 同城配對案例、偏好命中及違反率、人工盲評 |
| 操作協定是否減少錯誤修改？ | 文字解讀 vs. 結構化動作與確認 | 多輪語句矩陣、修改前後 DB diff、重播測試 |
| 背景化與串流改善了哪些等待？ | 同步 vs. 工作佇列；冷啟動 vs. 熱模型 | 首次內容、提交時間、完成時間及 P50／P95 |
| 規劃是否具備實際可行性？ | 現有規則 vs. 加入路線矩陣及時間窗 | 可信營業／交通資料、不可行行程比例 |

研究評估需固定模型與資料版本，將調參案例與保留測試案例分開，並報告失敗與缺資料情況。既有測試數量不能代替上述品質或使用者效益證據。
